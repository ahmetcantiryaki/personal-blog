Short answer: write a short spec with acceptance criteria, file boundaries, data contracts, a test plan, and non-goals, then hand it to Claude Code or Codex and review the agent's plan before it touches any file. Loose, conversational prompting ("vibe-prompting") works for a 20-line script; it falls apart once an agent generates most of a real feature.

## Why do written specs beat vibe-prompting now?

Because the volume of AI-written code has crossed the point where ambiguity compounds instead of washing out. Sonar's 2026 State of Code Developer Survey puts AI's share of committed code at 42% today, headed for 65% by 2027. JetBrains' 2026 Developer Ecosystem Survey, which polled over 15,000 professional developers, found roughly 47% of code is now fully generated by agents, 38% is written with AI assistance, and 27% is fully manual. GitHub reports 46% of code committed on its platform is AI-generated.

At that scale, a loosely specified prompt does not fail quietly. It produces a plausible-looking implementation that is wrong in a way the reviewer does not catch on a quick skim, it quietly expands scope beyond what anyone asked for, or — in a long agent session — it drifts further from the original intent with every turn. We have watched sessions that started from a one-line instruction and ended four hours later with a diff touching files nobody meant to touch. The trust numbers back this up: 96% of developers say they do not fully trust AI-generated code, and only 48% say they always verify it before committing. Vibe-prompting and "always verify" are in tension — a spec lets you verify against something concrete instead of your memory of what you meant to ask for.

| Vibe-prompting failure mode | Spec-driven fix |
|---|---|
| Plausible-but-wrong implementation that passes a skim | Acceptance criteria the agent (and reviewer) can check line by line |
| Scope creep nobody notices until the diff is huge | Explicit non-goals and file/module boundaries up front |
| Agent drifts from intent over a long session | Re-ground the agent in the written spec instead of patching with more ad hoc instructions |
| Reviewer has to reverse-engineer intent from the diff | Spec committed alongside the code as living documentation |

## What does an implementable spec actually need?

At minimum, five things: acceptance criteria, file and module boundaries, data contracts, a test plan, and explicit non-goals. Skip any one and the agent fills the gap with its own guess — exactly the behavior a spec exists to remove.

Acceptance criteria answer "how will I know this is done?" in terms a reviewer can check against running code, not the agent's own narration. File and module boundaries answer "what is this agent allowed to touch?" — without this, an agent asked to "add rate limiting" will happily refactor your auth middleware along the way, because nothing told it not to. Data contracts pin down input and output shapes: schemas, field types, error codes — things that break silently when an agent infers a shape instead of being told one. The test plan says which cases must pass before the work is finished, and non-goals say what the agent should explicitly *not* build, the single most effective lever against scope creep we have found.

Here is roughly how compact this can stay for a medium-sized feature:

```yaml
feature: rate-limit-login-endpoint
acceptance_criteria:
  - returns 429 after 5 failed attempts within 60 seconds, per IP+username pair
  - successful login resets the counter immediately
  - limit state survives a process restart (backed by Redis, not in-memory)
file_boundaries:
  allowed:
    - src/auth/rate_limiter.ts
    - src/auth/login_handler.ts
    - test/auth/rate_limiter.test.ts
  forbidden:
    - src/auth/session.ts
    - any file under src/db/migrations
data_contract:
  rate_limit_response:
    status: 429
    body: { error: string, retry_after_seconds: number }
test_plan:
  - unit: counter increments and resets correctly
  - integration: 6th attempt within window returns 429
  - integration: attempt after window expiry succeeds
non_goals:
  - do not add CAPTCHA
  - do not change the password hashing scheme
  - do not touch the signup endpoint
```

That spec reads in two minutes and is specific enough that an agent cannot plausibly wander outside it.

## How do you hand the spec to Claude Code or Codex?

You paste or reference the spec, then ask the agent to produce a plan before it edits a single file — reviewing a plan is far cheaper than reviewing a finished diff. Claude Code has an explicit plan-mode pattern built around this: the agent reads the spec, proposes an approach, and waits for a go-ahead before writing code. OpenAI's Codex follows the same logic, and it now also runs OpenAI's newest cost-efficient coding model, GPT-6.1 Sol, announced September 29, 2026 at DevDay and priced at $2 per million input tokens and $10 per million output tokens — near-flagship coding performance at a fraction of the cost.

That pricing move is itself an argument for specs over throwaway prompts. If instructions live only in a chat scrollback, switching models between agent runs means re-explaining everything from scratch. If they live in a spec file, you point a different agent or model at the same document and the intent carries over unchanged. Coding-agent economics move fast enough in late 2026 that this portability is not a nice-to-have — it is the difference between evaluating a new model in an afternoon and re-litigating a week of prompt history.

## What do you do when the agent drifts mid-session?

Stop and re-ground the agent in the written spec rather than patching the drift with more ad hoc instructions. The temptation, three or four turns into a session, is to nudge the agent back on track with another quick correction — "no, don't touch that file," "actually also handle this edge case." Each nudge feels cheap alone. Stacked across a long session, they turn into a second, unwritten spec that lives only in the conversation and contradicts parts of the first one.

The fix we keep coming back to: stop, re-paste the original spec, and ask the agent to re-check its current diff against it. This resets the agent's context to the actual source of truth instead of a pile of accumulated corrections, and it is usually faster than it feels like it should be — most drift traces back to one ambiguous line in the original prompt, not a dozen separate misunderstandings.

## How do you keep a spec useful after the PR merges?

Commit it alongside the code — as a `SPEC.md` in the relevant directory or as the PR description itself — so the next agent session, or the next human, reads the same source of truth instead of reverse-engineering intent from a diff. A spec that lived only in a chat window is gone the moment that window closes; a spec committed to the repository is readable by the next person who opens the file, and it is exactly the structured, explicit documentation that makes a repository easier for an agent to work in on the next pass. If your repo already uses an `AGENTS.md`-style file to orient agents generally, a per-feature spec is the same idea at a finer grain.

Small-PR discipline falls out of this almost automatically. When a spec produces a large, multi-concern diff, that is a sign the spec was too broad — it bundled decisions that should have been reviewed separately. Splitting a spec into smaller units, each with its own acceptance criteria and non-goals, keeps every resulting PR small enough for a human reviewer to hold in their head. Opinion: teams who resist this splitting end up skimming agent-generated PRs like a 2,000-line refactor, defeating the point of writing the spec at all.

## Frequently Asked Questions

### What is "vibe-prompting" and why does it stop working at scale?

Vibe-prompting means giving a coding agent loose, conversational instructions with no written spec, relying on back-and-forth chat to steer it. It works for small, disposable scripts, but once an agent produces most of a real feature's code, the ambiguity compounds into plausible-but-wrong implementations and undetected scope creep.

### What is Claude Code's plan mode?

Plan mode is a Claude Code pattern where the agent reads a spec, proposes an implementation plan, and pauses for human review before editing any files. A short plan is cheaper to review than a finished multi-file diff, which is why asking for a plan first is the recommended step.

### Do I need a spec for every small change?

No — a one-line bug fix or a trivial text change does not need acceptance criteria and a test plan. Roughly: if a change touches more than one file, involves a data contract, or would take more than a few minutes to review from a diff alone, write the spec first.
