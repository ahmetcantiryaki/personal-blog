Short answer: wrap your items in a `scroll-snap-type` container, add `scroll-marker-group`, `::scroll-marker`, and `::scroll-button()` for the dots and arrows, and the browser handles snapping, focus, and keyboard navigation. Chromium (Chrome and Edge 135+, April 2025) ships full support; Firefox and Safari fall back to a working scroll region with no dots or arrows, so the carousel degrades instead of breaking.

## What is a native CSS carousel?

A native CSS carousel is a scroll-snap container whose dots and navigation buttons are generated by the browser itself, through CSS pseudo-elements, instead of JavaScript — [Chrome for Developers' walkthrough of the feature](https://developer.chrome.com/blog/carousels-with-css) is the most detailed primary reference as of this writing. The three building blocks are `scroll-marker-group` (a container property that tells the browser to generate a strip of markers), `::scroll-marker` (one pseudo-element per scroll-snap child, styled like a dot or thumbnail), and `::scroll-button()` (prev/next arrow buttons tied to the scroll container).

Under the hood it's still the `scroll-snap-type` and `scroll-snap-align` properties that have shipped in every modern browser for years. What's new is that the browser can now also render the controls, which previously required a JavaScript library like Swiper or Slick to track scroll position and sync a dot indicator.

## How do you build one, step by step?

Start with a horizontally scrolling flex or grid container, mark it as a snap container, and mark each child as a snap target:

```css
.carousel {
  display: flex;
  overflow-x: auto;
  scroll-snap-type: x mandatory;
  scroll-marker-group: after;
  gap: 1rem;
}

.carousel > .slide {
  scroll-snap-align: start;
  flex: 0 0 100%;
}

.carousel > .slide::scroll-marker {
  content: "";
  width: 0.5rem;
  height: 0.5rem;
  border-radius: 50%;
  background: light-dark(#ccc, #555);
}

.carousel > .slide::scroll-marker:target-current {
  background: light-dark(#111, #eee);
}

.carousel::scroll-button(left) {
  content: "←";
}

.carousel::scroll-button(right) {
  content: "→";
}
```

`scroll-marker-group: after` places the generated dot strip after the carousel in the accessibility tree and visual order; `before` puts it ahead of the slides instead. The `:target-current` pseudo-class is what lets you style the active dot without a single line of JavaScript tracking scroll position.

## What keyboard and screen reader behavior do you get for free?

Each `::scroll-marker` is exposed as a real, focusable, clickable element — Tab reaches the dot strip, arrow keys move between markers in supporting browsers, and Enter or Space activates one to jump to that slide. The `::scroll-button()` elements behave like buttons: focusable, with a default disabled state at the start or end of the scroll range so users can't click past the last slide.

What you still have to add yourself: an `aria-label` on each `::scroll-marker` (a dot alone reads as nothing meaningful to a screen reader), a `aria-label` on the carousel container itself describing its purpose, and — if slides autoplay — a visible pause control, since autoplay without a pause button fails WCAG 2.2's 2.2.2 Pause, Stop, Hide criterion regardless of whether the carousel is built in CSS or JavaScript.

## Which browsers support this today?

As of November 2026, support is Chromium-first and still uneven elsewhere, so treat this as progressive enhancement rather than a drop-in replacement everywhere. [A 2026 deep-dive on scroll-driven CSS carousels](https://www.sitepoint.com/scrolldriven-css-in-2026-building-carousels-without-javascript/) tracks the same rollout and is worth a read before you commit to dropping a JS fallback entirely.

| Feature | Chrome / Edge | Firefox | Safari |
|---|---|---|---|
| `scroll-snap-type` / `scroll-snap-align` | Supported | Supported | Supported |
| `scroll-marker-group` | Supported since 135 (Apr 2025) | Not shipped | Not shipped |
| `::scroll-marker` | Supported since 135 | Behind a flag in some builds | Not shipped |
| `::scroll-button()` | Supported since 135 | Behind a flag in some builds | Not shipped |

Check the live tables on MDN or caniuse before shipping, since Firefox and Safari status changes release to release. Either way, the fallback is never a broken page: without the pseudo-elements, you get a working, swipeable, snapping scroll region with no dots or arrows — a functional carousel with degraded chrome, not a dead one.

## How do you handle the fallback gracefully?

Use `@supports selector(::scroll-marker)` to add JavaScript-free enhancements only where the browser can render them, and don't ship a loading spinner or empty box as the no-support state:

```css
@supports not selector(::scroll-marker) {
  .carousel-dots-fallback {
    display: flex;
  }
}

@supports selector(::scroll-marker) {
  .carousel-dots-fallback {
    display: none;
  }
}
```

That pattern — feature-detect with `@supports selector()`, show a minimal static fallback UI only when needed — keeps Safari and Firefox users with a usable carousel instead of a half-rendered one, and it avoids shipping a JavaScript polyfill solely to paint dots that CSS already draws natively where it's supported.

## Which JavaScript carousel libraries can you actually drop?

You can remove a scroll-tracking library entirely if your carousel only needs snapping, dot navigation, and prev/next buttons on supporting browsers, with a plain scroll as the fallback everywhere else. You still need JavaScript for autoplay with a pause control, infinite looping (CSS scroll-snap has no native loop-back), and synced external state (e.g., a counter outside the carousel reading "3 of 8"). For those cases, a thin ~2KB autoplay-and-loop script on top of native CSS snapping and markers is a much smaller dependency than a full carousel library like Swiper, which commonly ships 30-40KB minified.

My honest take: for simple image or testimonial carousels — the majority of what most sites actually ship — native CSS now covers the whole interaction, and pulling in a carousel library purely for dot navigation is no longer justified on a Chromium-majority traffic base. For [scroll-driven animations](/en/posts/scroll-driven-animations-in-css) layered on top, or [CSS anchor-positioned popovers](/en/posts/css-anchor-positioning-popovers-2026) next to a carousel, the same "ship it, let `@supports` handle the gap" pattern applies. Any carousel markup still needs to clear a [standard accessibility checklist](/en/posts/web-accessibility-checklist) — native markers don't exempt you from labeling and focus-order review.

## Frequently Asked Questions

### What CSS properties build a carousel without JavaScript?

`scroll-snap-type` and `scroll-snap-align` create the snapping scroll behavior, while `scroll-marker-group`, `::scroll-marker`, and `::scroll-button()` generate the dot navigation and prev/next buttons natively, without a JavaScript library.

### Do native CSS carousels work in Firefox and Safari?

Not fully as of November 2026. The underlying scroll-snap behavior works everywhere, but the `::scroll-marker` and `::scroll-button()` pseudo-elements are Chromium-only (Chrome/Edge 135+), with Firefox support behind a flag in some builds and no committed Safari timeline — check caniuse before relying on them.

### Is a native CSS carousel accessible by default?

Partially. Markers and buttons are focusable and keyboard-operable by default, but you still need to add `aria-label` text to each marker and the container, and you must add a manual pause control if slides autoplay, since WCAG 2.2.2 requires one regardless of implementation.

### Can I remove my carousel JavaScript library entirely?

Only if your carousel needs nothing beyond snapping, dots, and prev/next buttons. Keep a small script for autoplay with pause, infinite looping, or syncing an external slide counter — native CSS scroll-snap doesn't support any of those three on its own.
